Which JavaScript table library should you use?

We built the same table seven times, over 1,000 to 500,000 rows of UK property sales, to pick one for DataHub. Every grid below is live.

Use a plain <table> until it hurts, which is around a few thousand rows. Past that, AG Grid Community if you want it done, TanStack Table if you want it yours.

At 500,000 rows every virtualizing grid here scrolls at 60 fps and renders in 25 to 300 ms, and sorts them by price in 0.1 to 0.45 s. You cannot see those differences. So we picked on four other things: whether the text is in the DOM, what the bundle weighs, how it fails, and whether anyone is still shipping releases.

A table in a data story

Plain <table>

34 lines, 1 kB. Renders 1,000 rows in about 100 ms, which nobody notices. Prints, copies, sorts if you add ten lines, and dark mode is CSS.

Runner-up: Observable Inputs, sort on click in one call.
A big grid, least effort

AG Grid Community

500,000 rows at 60 fps with sort and filter built in, in 39 lines, any framework. It tells you when you have configured it wrong. It is 333 kB with every Community module registered, as the quick start does; registering only the six this demo uses brings it to 272 kB.

Runners-up: Tabulator, a third of the size, once you give it a sized parent; RevoGrid, the fastest DOM grid at 500,000 rows, if you accept its corner link.

TanStack Table + react-virtual DataHub's pick

A real <table> in your own markup, so Ctrl-F, select and copy work on the rows currently on screen. 24 kB on a page that already ships React. The cost is 146 lines you own.

Runner-up: Tabulator, if the portal is not React.

Tabulator

Four things that surprised us

  1. Render time does not separate the grids. Layout cost separates the grids from a <table>. The virtualizers all land between 25 and 300 ms at 500,000 rows. The plain table goes superlinear instead: 2.6 s at 50,000, 6.9 s at 100,000, about 27 s at 200,000, and we stopped waiting for 500,000 after ten minutes.
  2. The most dangerous line of code came from a library's own docs. Tabulator's height: "100%", the option its docs give for filling a container, renders every row when the parent has no resolved height: 62 seconds at 50,000 rows instead of 68 ms, with nothing logged. AG Grid fails visibly on the same mistake. Tabulator is a good library; the failure is the silence.
  3. Glide draws 500,000 rows faster than it draws 1,000, and RevoGrid nearly matches it in real DOM. Glide is canvas: it paints a fixed viewport and never touches the data, browser Ctrl-F and text selection cannot see it. Its own range copy works once you set getCellsForSelection, which the quick start does not mention. Its last release was February 2024, which is why it is only a runner-up. RevoGrid, a web component few shortlists include, rendered 500,000 rows in 55 ms with real cells, in any framework.
  4. Headless means you write the virtualizer. TanStack Table is the smallest React bundle here and the most lines of code. The row and column virtualizers, the spacer cells, the sticky header and the sort arrows are all ours. What comes back is an ordinary <table>.

What we measured

Own code is gzipped JS + CSS with the shared harness netted out, read from the build. Render time and scroll FPS are typed in from one run (one laptop, headless Chromium; Sep 2026). Treat them as an order of magnitude. Every virtualizing grid hit the 60 fps ceiling, so that column separates little. Every demo page measures again in your browser.

Footnotes and how to read the columns
  • a Observable Inputs appends rows as you scroll and never removes them. The 6.7 ms is the first 60-row batch, not 500,000 rows. Scroll to the bottom and every row is live in the DOM, all 80 columns of the wide set included.
  • b Tabulator's documented height: "100%" replaces the host's CSS height with one the parent cannot resolve, so it measures a 0 px viewport and renders every row: 62 s at 50,000. Give the host a real height and it is 280 ms. Nothing warns either way.
  • c Glide's 500,000 rows render faster than its 1,000 because canvas paints a fixed viewport. Nothing on screen is in the DOM. It keeps a hidden role="grid" mirror of the visible rows for screen readers. Selecting a range and pressing Ctrl/Cmd-C copies it as tab-separated text once getCellsForSelection is set; browser Ctrl-F and text selection get nothing.
  • e DataTables builds its whole row model, with type detection and an autoWidth scan, before Scroller windows anything; its own FAQ caps client-side data at about 50,000 rows. autoWidth: false cuts a third to a half. No column virtualization, so the 80-column card is its slowest.
  • f RevoGrid's loader fetches about 88 kB of component code when the first grid connects, so the build-time figure understates it: about 118 kB is the real cost on first render. Its aftergridrender event fires before any cell exists; the demo waits for the first real cell instead.
  • g AG Grid's own-code figure is with AllCommunityModule registered, as its quick start does, and that is what this site ships. Built again through the same pipeline with only the modules the demo uses (ClientSideRowModelModule, the text, number and date filters, CellStyleModule and NumberEditorModule; sorting and resize are core), it is 272 kB against 334 kB for everything. Sort, filter and edit still work, with no missing-module errors. Measured by scripts/measure-aggrid-lean.mjs.
  • d Perspective's large figure is mostly moving 500,000 JavaScript objects into a worker and rebuilding them as Arrow columns. Every library gets the same Array<Object>, which is Perspective's worst input; Arrow or CSV would cut it. Its WASM boot is timed separately and shown as "engine ready in N ms" on its page and in the gallery, not inside any render figure. Once loaded, sort and filter run in the worker.
  • Own code nets out the 25 kB every demo page loads (the mount harness, the Parquet reader, site.css) and, for the React demos, 60 kB of React. Full page weights are in bundles.json. Perspective's WebAssembly is its own column because gzip barely compresses it.
  • Lines written are non-blank, non-comment lines under src/demos/<key>/. A build-cost proxy: JSX markup counts the same as logic. The sort hook and edit test that the harness asks of each demo are fenced off and not counted, so the column still measures building the table.
  • The render clock covers building the DOM and a forced layout. Without the layout flush the plain <table> would report a fifth of its real cost. Scroll FPS is a scripted scroll of 20,000 px over 120 frames on the element that actually moves. It is a short traversal of 20,000 px. Timings so far are from the Vite dev server; the re-measure runs on the production build.
  • Sort by price is the button on each large card: the rows go back to file order (untimed), then the library's own sort call is timed until the sorted rows are on screen, with the same clock as a render (layout forced, async engines awaited, Glide's canvas redrawn). Median of 5 (21 Nov 2026). Glide has no sort of its own, so its figure is our index sort plus a redraw; Observable Inputs sorts every row but draws only the first 60. The plain table sorts the 100,000 rows it shows and rebuilds them, which is why it takes tens of seconds.
  • Ctrl-F finds only mounted cells, meaning the rows on screen plus a small buffer, in every virtualized DOM grid here (Tabulator, AG Grid, TanStack, Perspective, DataTables with Scroller, RevoGrid). It finds nothing in Glide, which is canvas. The plain <table> has every row in the DOM, and Observable Inputs has every row it has appended so far. Searching the whole dataset needs the library's own search or filter.
  • Heap is not a column. Chrome pins performance.memory to a placeholder unless started with --enable-precise-memory-info, so any figure would have been invented.
  • Cells with a tooltip are from a run being repeated on the versions shown; the number may move a little.

Method

Same four datasets, same page shell, same theme tokens, same cell formatter and the same mounting harness for every entry. Each demo supplies four render functions; the harness owns the page, the clock and the FPS run, and empties the host between renders. The clock waits for async work and forces layout, so a library that returns early cannot report a scheduling call as a render. Agents built most of the demos under direction; the numbers were checked against the build and the live pages before they went on this page.

The full method and its caveats: ANALYSIS.md. The verdict with its reasoning: EVALUATION.md. Datasets: HM Land Registry Price Paid data as Parquet. Small is 1,000 sales in 16 columns; wide is the same 1,000 with 64 derived numeric columns; medium is 50,000 rows; large is a 500,000-row sample of one year, loaded on demand.

Considered, not included

  • Handsontable: paid for commercial use since v7. Everything here is permissive open source.
  • MUI X Data Grid: the MIT tier caps pages at 100 rows and keeps column pinning, tree data and aggregation in Pro and Premium. Theming runs through MUI's system, so it could not take this site's tokens the way the others did.
  • react-data-grid: still a beta after years, and React 19 only. The TanStack demo already answers "a virtualized <table> in React".
  • SlickGrid: 6.0 (Nov 2026) is real and MIT, and it shows what AG Grid and Tabulator already show here.
  • Grid.js: no release since March 2024.
  • Kendo, DevExtreme, Syncfusion, Bryntum: commercial. This is about libraries you can adopt without a procurement conversation.
  • Vue, Svelte, Angular grids: TanStack has adapters for all three, and the vanilla entries work anywhere. Glide is React only.
