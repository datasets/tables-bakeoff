What we measured

Treat them as an order of magnitude. Most grids hit the 60 fps ceiling, so that column separates little, and a smooth scroll says nothing about how long the first render or a sort takes. Footnotes and how to read the columns
  • a Observable Inputs appends rows as you scroll and never removes them. The 10.8 ms is the first 60-row batch, not 500,000 rows. Scroll to the bottom and every row is live in the DOM, all 80 columns of the wide set included.
  • b Tabulator's documented height: "100%" replaces the host's CSS height with one the parent cannot resolve, so it measures a 0 px viewport and renders every row: 88 s at 50,000 rows. Give the host a real height and the same 50,000 rows take 36 ms. Nothing warns either way.
  • c Glide's 500,000 rows render as fast as its 1,000 (17 and 19 ms) because canvas paints a fixed viewport. Nothing on screen is in the DOM. It keeps a hidden role="grid" mirror of the visible rows, meant for screen readers; we did not test one. Selecting a range and pressing Ctrl/Cmd-C copies it as tab-separated text once getCellsForSelection is set; browser Ctrl-F and text selection get nothing.
  • e DataTables builds its whole row model, with type detection and an autoWidth scan, before Scroller windows anything; its own FAQ caps client-side data at about 50,000 rows. autoWidth: false cuts a third to a half. No column virtualization, so the 80-column card is its slowest.
  • f RevoGrid's loader fetches about 88 kB of component code when the first grid connects, so the build-time figure understates it: about 118 kB is the real cost on first render. Its aftergridrender event fires before any cell exists; the demo waits for the first real cell instead.
  • g AG Grid's own-code figure is with AllCommunityModule registered, as its quick start does, and that is what this site ships. Built again through the same pipeline with only the modules the demo uses (ClientSideRowModelModule, the text, number and date filters, CellStyleModule and NumberEditorModule; sorting and resize are core), it is 272 kB against 334 kB for everything. Sort, filter and edit still work, with no missing-module errors. Measured by scripts/measure-aggrid-lean.mjs.
  • h Text in the DOM, browser text selection, grid copy and accessibility are four different things. Every grid here except Glide puts the visible cells in the DOM. Select text is a mouse drag across a cell: it works in the plain table, Observable, Tabulator, TanStack and DataTables. AG Grid draws grid markup (div role="grid"), not a <table>, and blocks selection unless you set enableCellTextSelection, which our demo does not. Perspective and RevoGrid turn it off too. Grid copy (select a range, Ctrl/Cmd-C) is a library feature: Glide with getCellsForSelection, RevoGrid by default, Tabulator with clipboard: true, AG Grid only in Enterprise. Keyboard sort: Tab from the top of the 1,000-row embed until a column header has focus, press Enter, check the rows moved. AG Grid, DataTables and TanStack sort. Observable, Tabulator, Perspective and RevoGrid sort on a click, but Tab never reaches a header. The plain table and Glide demos have no header sort. Not tested: screen readers, arrow-key navigation inside the grid, focus handling while scrolling.
  • d Perspective's large figure is mostly moving 500,000 JavaScript objects into a worker and rebuilding them as Arrow columns. Every library gets the same Array<Object>, which is Perspective's worst input; Arrow or CSV would cut it. Its WASM boot is timed separately and shown as "engine ready in N ms" on its page and in the gallery, not inside any render figure. Once loaded, sort and filter run in the worker.
  • Own code nets out the 25 kB every demo page loads (the mount harness, the Parquet reader, site.css) and, for the React demos, 60 kB of React. Full page weights are in bundles.json. Perspective's WebAssembly is its own column because gzip barely compresses it.
  • Lines written are non-blank, non-comment lines under src/demos/<key>/. A build-cost proxy: JSX markup counts the same as logic. The sort hook and edit test that the harness asks of each demo are fenced off and not counted, so the column still measures building the table.
  • The render clock covers building the DOM and a forced layout. Without the layout flush the plain <table> would report a fifth of its real cost. Scroll FPS is a scripted scroll of 20,000 px over 120 frames on the element that scrolls. All figures here are from the production build.
  • Sort by price is the button on each large card: the rows go back to file order (untimed), then the library's own sort call is timed until the sorted rows are on screen, with the same clock as a render (layout forced, async engines awaited, Glide's canvas redrawn). Median of 5 fresh page loads. Glide has no sort of its own, so its figure is our index sort plus a redraw; Observable Inputs sorts every row but draws only the first 60. The plain table sorts the 100,000 rows it shows and rebuilds them, which is why it takes tens of seconds.
  • Ctrl-F finds only mounted cells, meaning the rows on screen plus a small buffer, in every virtualized DOM grid here (Tabulator, AG Grid, TanStack, Perspective, DataTables with Scroller, RevoGrid). It finds nothing in Glide, which is canvas. The plain <table> has every row in the DOM, and Observable Inputs has every row it has appended so far. Searching the whole dataset needs the library's own search or filter.
  • Heap is not a column. Chrome pins performance.memory to a placeholder unless started with --enable-precise-memory-info, so any figure would have been invented.
  • Cells with a tooltip are from a run being repeated on the versions shown; the number may move a little.

Four things that surprised us

  1. Render time does not separate the fast grids. The gap is between any virtualized grid and a plain <table>. Five virtualizers land between 17 and 233 ms at 500,000 rows; Perspective takes 1.9 s and DataTables 8.5 s. The plain table goes superlinear instead: 2.5 s at 50,000, 6.3 s at 100,000, about 27 s at 200,000, and we stopped waiting for 500,000 after ten minutes.
  2. The worst failure came from a line in a library's own docs. Tabulator's height: "100%", the option its docs give for filling a container, renders every row when the parent has no resolved height: 88 seconds at 50,000 rows instead of 36 ms, with nothing logged. AG Grid fails visibly on the same mistake. Tabulator is a good library; this option fails without a warning.
  3. Glide draws 500,000 rows as fast as it draws 1,000, and RevoGrid is not far behind in real DOM. Glide is canvas: it paints a fixed viewport, so browser Ctrl-F and text selection cannot see the cells. Its own range copy works once you set getCellsForSelection, which the quick start does not mention. Its last release was February 2024, which is why it is not a pick. RevoGrid, a web component, rendered 500,000 rows in 62 ms with real cells, in any framework.
  4. Headless means you write the virtualizer. TanStack Table is the smallest React bundle here and the most lines of code. The row and column virtualizers, the spacer cells, the sticky header and the sort buttons are all in the demo's code. What comes back is an ordinary <table>.

Method

Same four datasets, same page shell, same theme tokens and the same mounting harness for every entry, and the same cell formatter for all but Perspective, which has no per-cell formatter hook. Each demo supplies four render functions; the harness runs the page, the clock and the FPS test, and empties the host between renders. The clock waits for async work and forces layout, so a library that returns early cannot report a scheduling call as a render. Agents built and measured the demos under our direction. We chose the verdict, and every timing but one comes from a script in the repo you can run yourself (scripts/measure-all.mjs); the Tabulator 88 seconds was timed by hand.

Datasets: HM Land Registry Price Paid data as Parquet. Small is 1,000 sales in 16 columns; wide is the same 1,000 with 64 derived numeric columns; medium is 50,000 rows; large is a 500,000-row sample of one year, loaded on demand.
